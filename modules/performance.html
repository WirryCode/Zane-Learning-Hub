HTML Performance

Core Web Vitals, TTFB, caching, resource hints, images

A fast site starts with a fast HTML response, and then depends on how well your markup tells the browser what to fetch first. This module covers both halves: the server side of the first request (redirects, caching, compression, CDNs) and the markup side (scripts, resource hints, images, DOM size), measured with the Core Web Vitals.

2. The first request: HTML and TTFB

Typing a URL sends a GET request for HTML. Every step before the first byte adds to TTFB, and a slow TTFB makes good LCP and FCP hard to reach.

Minimise redirects

  • A 301/308 (permanent) or 302/307 (temporary) redirect costs an extra round trip to the new URL.
  • Same-origin redirects are yours to fix. Cross-origin ones (ads, URL shorteners) are not, but avoid chains such as http:// to https:// to www.
  • Link directly to the final URL. A common waste is /page/ redirecting to /page (or the reverse): link to the form that does not redirect.

Cache HTML carefully

  • HTML references fingerprinted CSS, JS and images, so a cached page can point at old files after a deploy. A short lifetime still beats none: it lets a CDN absorb requests and lets browsers revalidate. Five minutes (Cache-Control: max-age=300) is a safe starting point for static pages.
  • Personalised HTML (a logged-in user) should usually not be cached at all: a cached copy cannot be invalidated from the server.
  • Revalidation: the server sends an ETag (a hash of the content). The browser returns it in If-None-Match; if it matches, the server replies 304 Not Modified with no body. Last-Modified works the same way with dates. It still costs a round trip.
  • no-cache does not mean "do not cache": it means "revalidate before using". no-store means never store. For static assets with hashed names, use Cache-Control: public, max-age=31536000, immutable.

Measure the server

  • A dynamically built page (database queries) usually has a higher TTFB than a static file. Moving the work to the client with a spinner pushes it to a less predictable environment and usually hurts user-centric metrics.
  • Expose where server time goes with the Server-Timing header, e.g. Server-Timing: auth;dur=55.5, db;dur=220 (authentication 55.5 ms, database 220 ms). Collect it from real users with the Navigation Timing API.
  • Check hosting capacity: shared hosting often has a high TTFB.

Compress text

  • Compress HTML, CSS, JavaScript, SVG and JSON. Brotli beats gzip by roughly 15 to 20%, works in all major browsers (over HTTPS), and gzip remains the fallback. Any compression beats none. Do not compress already-compressed images, video or fonts like WOFF2.
  • Very small files (under about 1 KiB) compress poorly. Do not ship a huge file merely because it compresses well: big JS and CSS cost parse time after decompression.
  • Static compression (done at build time) suits CSS, JS and SVG. Dynamic compression (done per request) suits generated HTML.

Use a CDN

A Content Delivery Network is a distributed set of servers that cache your content at edge servers physically close to users. It cuts round-trip time and adds HTTP/2 or HTTP/3, caching and compression, often improving TTFB.

3. Loading resources from the markup

Scripts and CSS

  • CSS is render-blocking: the browser will not paint until it has the CSS in the head. Keep it small. A <link rel="stylesheet" media="print"> is not render-blocking for screen.
  • A classic <script src> is parser-blocking. Add defer (download in parallel, run in order after parsing) or async (run as soon as downloaded, any order). type="module" scripts defer by default.
  • Do not put third-party scripts in the critical path; load them late or with async.

Images

  • Always set width and height (unitless pixels) on <img> and <video>. The browser uses them to compute an aspect ratio and reserve space before the file arrives, preventing layout shift. Add img { max-width: 100%; height: auto } for responsive scaling.
  • loading="lazy" on images and iframes below the fold. Never on the LCP image or anything visible at load.
  • fetchpriority="high" on the LCP image; fetchpriority="low" on unimportant ones. It is a hint.
  • srcset and sizes (or <picture>) send small files to small screens; use AVIF or WebP with a fallback. decoding="async" keeps decoding off the main thread.

4. DOM size and rendering cost

  • Every node costs memory and makes style calculation and layout slower, especially after changes. Lighthouse warns above roughly 800 nodes and flags an excessive DOM above about 1,400, deep nesting (over about 32 levels) and parents with over about 60 children.
  • Count nodes: document.getElementsByTagName('*').length. Remove wrapper <div>s, paginate or virtualise long lists, and render off-screen sections lazily with content-visibility: auto.
  • Avoid layout thrashing: alternating reads (offsetHeight) and writes (style.height = ...) in a loop forces repeated layout. Batch reads first, then writes.
  • Reduce JavaScript before reducing anything else for INP: long tasks block the next paint. Break them up and do less on the main thread.
⚠ Common mistakeLazy-loading the hero imageloading="lazy" on the largest above-the-fold image delays it until layout is known and wrecks LCP. Lazy-load only what is below the fold; give the hero fetchpriority="high".
⚠ Common mistakePreloading everythingEach preload competes for bandwidth with the real critical resources. Preload only what the browser would find late and certainly use; an unused preload triggers a console warning and wastes data.
⚡ Pro hackPriority in one attribute<img src="hero.avif" fetchpriority="high"> boosts the LCP image without a preload tag, and fetchpriority="low" on a carousel's later slides frees bandwidth. Check the effect in DevTools' Network "Priority" column.
⚡ Pro hackSkip rendering off-screen sectionssection.below-fold { content-visibility: auto; contain-intrinsic-size: auto 600px; } lets the browser skip layout and paint for sections that are not yet near the viewport.
☠ Major fail pointImages with no dimensionsWithout width and height the box is 0 tall until the file downloads, then everything below jumps. That is the commonest source of CLS, and it is a free fix.
☠ Major fail pointBlocking script in the headA plain <script src> in <head> stops the parser: nothing after it renders until it downloads and runs. Use defer, or async for independent scripts.
☠ Major fail pointCaching personalised HTMLServing a cached page that includes one user's name or basket to another is a privacy bug, not a speed-up. Use Cache-Control: private, no-store (or vary correctly) for per-user HTML.
