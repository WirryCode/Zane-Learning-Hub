Semantics

Meaningful markup and the accessibility tree

Semantic means "relating to meaning". Semantic HTML picks each element for what the content is, not for how it looks. Looks are CSS's job. Meaning is for browsers, search engines, screen readers and the next developer.

1. Div soup vs meaningful markup

Both snippets can look identical. Only the second tells a machine (or a person who cannot read the language) what each part is.

<!-- Div soup: boxes and text, no meaning -->
<div><span>Machine Learning Workshop</span>
  <div><a href="/">Home</a> <a href="/about">About</a></div></div>
<div><div>Enrolment is open</div>
  <div><div>Why enrol</div><div>Because machines.</div></div></div>
<div><span>&copy; 2026</span></div>

<!-- Semantic: structure is obvious at a glance -->
<header><h1>Machine Learning Workshop</h1>
  <nav><a href="/">Home</a> <a href="/about">About</a></nav></header>
<main><h2>Enrolment is open</h2>
  <section><h3>Why enrol</h3><p>Because machines.</p></section></main>
<footer><p>&copy; 2026</p></footer>
🧠 Remember itMOLE: the semantic mindsetMoles Only Like Earthworms = Meaning Over Looks, Every time. Choose the tag for what the content is; style it with CSS.

2. Three trees the browser builds

TreeBuilt fromUsed by
DOMHTML nodes (elements, attributes, text)JavaScript, selectors
CSSOMStylesheetsRendering
Accessibility tree (AOM)DOM + computed styles + rolesScreen readers, voice assistants

Each node in the accessibility tree exposes a name, a role and a state or value. Div soup produces a tree of bare text and links. Semantic markup produces named landmarks, headings and lists that users can jump between by keyboard. HTML is accessible by default; your job is to not break that.

⚡ Pro hackSee the accessibility treeChrome: DevTools, Elements, Accessibility tab. Firefox: the Accessibility panel. Click a node to see its role, name and state. No landmarks showing? Your page is div soup.
✎ Notes corrected: the notes call the AOM "a semantic version of the DOM". More exactly, it is the accessibility tree browsers derive from the DOM and computed style, so display:none removes nodes from it. Also, the notes' Firefox shot labels a <header> nested in <main> as a "section": it is not a landmark (ARIA calls it generic).

Roles matter because they tell a user what an element is and how to interact with it. Landmarks make large pages keyboard-navigable.

4. The role attribute (and why to avoid it)

role is a global attribute defined by the ARIA spec, not the HTML spec. It changes what assistive technology announces. It does not change appearance, focus or behaviour.

The div has tabIndex -1 (not in the tab order) and ignores Enter and Space. The <button> gets focus, both keys and the HTMLButtonElement API for free. Rebuilding that on a div means tabindex, key handlers and styles.

🧠 Remember itFROG: the first rule of ARIAFirst Rule Of ARIA: Go native. Use the real element first. Add ARIA only when no element fits.
⚠ Common mistakeRole on a div<div role="button"> only announces a button. It is still unfocusable and keyboard-dead until you add tabindex="0" and key handlers.
⚠ Common mistakeRedundant roles<button role="button"> or <nav role="navigation"> adds nothing. Quiz-style answer: you should never add role="button" to a <button>.
✎ Notes corrected: the notes' div-with-roles example has mismatched quotes (role="banner') and the <p role="button"> line is mangled by entities. Also add that "no ARIA is better than bad ARIA".

5. Choosing the right element

  • Ask: "Which element best represents the function of this markup?"
  • Never pick an element for its default look (an <h3> because it is smaller, a <blockquote> to indent, a <br> for spacing).
  • <div> and <span> are fine as last-resort styling hooks when nothing else fits.
  • Right elements mean no refactoring comments like <!-- end header -->.
⚡ Pro hackTurn off the CSS testDisable styles (or tab through with the keyboard). If the reading order still makes sense, with headings, lists and landmarks, your semantics are sound.
☠ Major fail pointARIA that removes meaningrole="presentation" or aria-hidden="true" on a focusable element hides it from screen readers while it stays in the tab order. Focus lands on "nothing". Bad ARIA is worse than no ARIA.
☠ Major fail pointDiv soup + click handlersA page of divs has no landmarks, no headings, no keyboard access. Screen reader users cannot skim it, so they leave.
