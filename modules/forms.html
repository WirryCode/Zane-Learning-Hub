Forms

Inputs, labels, validation, fieldsets

A <form> collects input and sends it to a server, and HTML alone can do a surprising amount of this: required fields, patterns, ranges, even submitting and loading a new page, all without JavaScript. This module covers the structure, the submitted data, labels, and built-in validation.

1. The form element

  • <form> wraps the controls. It is a landmark only when it has an accessible name (aria-label or aria-labelledby); an unnamed form is generic.
  • action: the URL that processes the data (default: the current page).
  • method: get (default) puts name=value pairs in the URL; post puts them in the request body. Use post for passwords, personal data and anything that changes state. (And serve it over HTTPS.)
  • method="dialog" inside a <dialog> closes the dialog and sets its returnValue; nothing is sent.
  • enctype: application/x-www-form-urlencoded (default), multipart/form-data (required for file uploads), text/plain.
  • novalidate on the form switches off built-in validation.
  • form="id" on a control (or <fieldset>, <button>, <output>) attaches it to a form it is not nested in. An empty or wrong value detaches it from its own form!
<form action="/enrol" method="post" aria-label="Workshop registration">
  <label for="full_name">Your name</label>
  <input type="text" id="full_name" name="name" required>
  <button type="submit">Enrol</button>
</form>

2. Buttons and overrides

  • Two ways to write a submit button: <input type="submit" value="Send"> (label from value) or <button type="submit">Send</button> (label from content, can hold markup).
  • <button> inside a form defaults to submit. Say type="button" for buttons that should not submit, and type="reset" to clear.
  • A button's formaction, formenctype, formmethod, formnovalidate and formtarget override the form's action, enctype, method, novalidate and target for that click.
  • Typical "Save draft" button: <button formnovalidate>. Typical "Cancel" in a dialog: formmethod="dialog" formnovalidate.
  • Only the clicked submit button is sent, and only if it has a name.

3. What gets submitted

The browser sends one name=value pair for each successful control. A control is sent only if it has a name, is not disabled, and (for checkboxes and radios) is checked.

  • Value: the value attribute, or what the user typed or picked. A <textarea>'s value is its text. An <option> without value sends its inner text.
  • Unchecked checkboxes and radios send nothing. A checked checkbox with no value sends on.
  • A named text control left empty still sends name= with an empty value.
  • readonly controls are sent; disabled ones are not.
  • Controls the user cannot edit (hidden, radio, checkbox, submit, button, reset) should always carry a value.
  • A <fieldset> and an <output> are not submitted (their named children are).
<!-- picking the 2nd option and submitting a GET form: -->
<select name="student">
  <option value="hoover">Hoover Sukhdeep</option>
  <option>Blendan Smooth</option>     <!-- no value: inner text is sent -->
</select>
<!-- ?student=hoover   or   ?student=Blendan+Smooth -->

4. Radios and checkboxes

  • Radios in one group share the same name; only one can be selected. Give each a different value. Two separate questions accidentally sharing a name will cancel each other out.
  • checked pre-selects one. It matches :default for ever, while the current selection matches :checked.
  • To require a choice, put required on at least one radio of the group.
  • Checkboxes in a group may share a name (all selected values are sent as repeated pairs: chk=a&chk=b). Always give them values, or you get chk=on&chk=on.
  • required on a checkbox only affects that checkbox.

5. Labels and fieldsets

  • Every control except buttons needs a label. A button's name comes from its content or value.
  • Explicit: <label for="id"> plus id on the control. Implicit: nest the control inside the label.
  • Labels are click targets too, which helps dexterity issues and thick fingers.
  • No links or other interactive elements inside a label.
  • placeholder is a hint, not a label: it vanishes when typing and has weak contrast.
  • Label a group with <fieldset> and <legend> (radios, checkboxes, address blocks). Fieldsets can nest. disabled on a fieldset disables everything inside it (except the first legend's content).
⚠ Common mistakeTwo radio groups, one nameReusing name="choice" for two separate questions makes them one group: picking in the second silently unpicks the first. Each question needs its own name.
☠ Major fail pointPlaceholder as the only labelScreen readers may skip it, it disappears as soon as the user types, and the grey text fails contrast. Use a real <label>.

6. Input types, keyboards and files

  • There are 22 input types: button, checkbox, color, date, datetime-local, email, file, hidden, image, month, number, password, radio, range, reset, search, submit, tel, text, time, url, week.
  • On phones the type picks the keyboard: tel shows a keypad, email adds @, url adds /. inputmode and enterkeyhint fine-tune it without changing validation.
  • type="file": accept limits kinds (image/*, video/*, audio/*, .pdf or a comma list). capture="user" or "environment" asks a phone for the front or back camera. multiple allows several files. Remember enctype="multipart/form-data".
  • <input type="image"> is a graphical submit button that sends the click's x and y coordinates (cross-reference: Images module).
  • autocomplete (email, given-name, postal-code, new-password, one-time-code...) enables fast, accessible completion. Use it.
  • Related controls: <select>, <textarea>, <datalist> (suggestions), <output> (computed result), <progress>, <meter>.

7. Built-in constraint validation

When the user submits, the browser checks each control's constraints. If any fail, submission is cancelled, the first bad control gets focus and an error bubble. No JavaScript needed.

🧠 Remember itRPMMSLT: validation attributesReally Pink Monkeys Make Sticky Lemon Tea = required, pattern, min, max, step, length, type.
  • An empty, non-required field never fails pattern. An empty required one reports valueMissing instead.
  • type="email" accepts a@b, so add pattern if you need a dot.
  • maxlength stops typing at the limit, which can feel hostile. A visible counter (an <output>) with a softer rule is often kinder.
  • CSS reacts live: :required, :optional, :valid, :invalid, :in-range, :out-of-range, :read-only, :read-write, :disabled, :enabled, :default. :user-invalid and :user-valid wait until the user has interacted, so you can avoid shouting errors at an untouched form.
  • novalidate (form) or formnovalidate (button) skips the check.
  • JavaScript hooks: form.checkValidity(), form.reportValidity(), input.setCustomValidity("msg") (a method on the control, not on validity). A custom message blocks submission until you reset it with setCustomValidity("").
