Focus

tabindex, autofocus, keyboard flow

Focus is the element that currently receives keyboard input. Interactive elements (links with href, buttons, form controls, <summary>, editable content, iframes) are focusable and tabbable by default: they join the sequential focus navigation order, which follows the source order. Everything else is inert: not interactive. HTML attributes can change both groups.

Terms to keep apart: focusable = can receive focus (click, script, or Tab). Tabbable = reachable by pressing Tab. Every tabbable element is focusable; not every focusable one is tabbable.

1. Always show where focus is

  • Keyboard users need a visible indicator. Style :focus-visible (shown for keyboard use), :focus and, for a parent whose child is focused, :focus-within.
  • Never write outline: none without a replacement of equal visibility.
  • Test by tabbing through the page; Shift+Tab goes backwards.
🧠 Remember itSPOT: focus checklistSeals Prefer Oily Tuna = Show focus, Preserve the outline, keep Order logical, Test with the keyboard.
☠ Major fail pointoutline: noneRemoving the focus ring "because it is ugly" leaves keyboard users lost. If you restyle it, make the new indicator at least as visible (outline: 3px solid; outline-offset: 2px).

2. Do not scramble the order

Default focus order = visual order = source order. Two things break it:

  • HTML: positive tabindex values.
  • CSS: flex-direction: row-reverse, the order property, grid placement, absolute positioning, transforms and multi-column can move things on screen while the tab sequence stays in the code order.

The result is focus that jumps around the screen. Keep a logical order at every viewport size, and if the visual order must change, change the source order instead.

⚠ Common mistakeReordering with CSS onlyA flex layout reversed with order: -1 looks perfect to the mouse and is chaos to Tab. WCAG calls this a failure of "Focus Order" and "Meaningful Sequence".

3. Make inert elements focusable

  • tabindex="0" on something already focusable (button, link) is unnecessary.
  • tabindex="-1" on an interactive element removes it from the Tab order but does not disable it: mouse users can still focus and click it.
  • el.focus() focuses an element and the browser scrolls it into view. Use document.activeElement to read which element has focus. Avoid focus({preventScroll:true}) unless the element is already visible.
  • A custom element used as a control needs the whole contract: tabindex="0", a role, and key handling for Enter and Space. Prefer the real element.
🧠 Remember itTDI: three ways to take things out of TabTigers Dislike Ice = negative Tabindex, Disabled, Inert. They look alike but are not interchangeable.

contenteditable

contenteditable="true" makes the element editable, focusable and tabbable (similar to tabindex="0"). A nested editable element is focusable but not tabbable until you add tabindex="0".

autofocus

  • autofocus is a global boolean. On page load, the first focusable element with it gets focus, and the page scrolls to it. It does not make an inert element interactive.
  • Problems: screen reader users may miss the instructions or label above it; it moves the starting point of Tab so earlier content is skipped. Avoid it on ordinary pages.
  • Exception: inside a <dialog>. Opening a dialog focuses its first focusable element, and autofocus lets you choose a different one (such as the safe "Cancel" button of a destructive prompt).
<dialog open>
  <form method="dialog">
    <button type="submit" autofocus>Close</button>
  </form>
</dialog>

  • disabled is a boolean: you cannot set it to false. Remove it (removeAttribute) or set el.disabled = false. On a <fieldset> it disables all descendants except those in the first <legend>.
  • inert is meant for sections: off-screen drawers, background content behind a modal, a form while it is submitting. A modal <dialog> opened with showModal() makes the rest of the page inert for you.
  • Make inertness visible with CSS (dim it). Never leave the focus on, or move it to, something hidden or inert.
  • Content that is hidden but appears when focused (a skip link) must not be inert.
⚡ Pro hackRoving tabindexFor a toolbar or tab list, keep one item at tabindex="0" and the rest at -1; move the 0 with the arrow keys. The group is one Tab stop and arrows move within it.
⚡ Pro hackFocus the heading after a route changeAfter swapping content in a single-page app, give the new <h1> tabindex="-1" and call .focus() so screen reader and keyboard users land at the top of the new view.
☠ Major fail pointFocus into the voidShowing a panel with visibility:hidden/off-screen positioning but leaving its links tabbable lets focus vanish into invisible content. Make off-screen content inert (or hidden).
⚠ Common mistakeUsing disabled for everythingdisabled removes the control from the form data and from view of assistive tech users who might wonder why. If a field is just not editable but should be sent, use readonly. If the control should stay tabbable, explain why in text instead.
